# 指示テンプレ（docs/prompts/）

フェーズごとにAIへ渡す指示文を置く。**案件ごとに書き換えるのは `docs/p00-brief.md` だけ**で、
ここの指示文は書き換えない。書き換えたくなったらテンプレ側の不足なので、指示文そのものを直す。

## 原則

- **1フェーズ1指示、1セッション。** 前フェーズの会話を引き継がない。入力は常にファイル。
- **会話ではなくファイルがインターフェース。** 口頭で足した前提は、ファイルへ書くまで存在しない扱い。
- **スコープの上限を毎回明記する。** 「ここまで。次フェーズに踏み込むな」が無いと必ず越境する。

## 人とAIの分担

全部をAIに任せない。RDRA 公式は「要件はヒアリングしてまとめるのではなく、業務を理解し**組み立てる**」
「答えのない中で要求から要件を決める」としており、決める行為は人の仕事である。

- **Step1〜4（発散）** — AI が速い。粗く洗い出すだけなので代行させてよい
- **Step5〜6（組み立て）** — 人が主、AI は整合チェック係。全工数の約半分がここ
- **Step7〜9（ビジネスルール）** — 人。業務知識そのものなので AI が書くと嘘になる

**ステークホルダーと議論しながらその場で直す局面に、Markdown と git は向かない。**
議論は書き換えやすい道具（表・図・ホワイトボード）で行い、合意した**結果**だけをここへ落とす。
`docs/` は議論の場ではなく、結果を固定してトレース可能にする場である。

## ゲートの扱い

- 人が止まるのは **G1（要件FIX）と G3（デザインFIX）の2箇所だけ**。
- G2 / G4 は `scripts/docs-validate/validate-docs.py` の機械判定のみで、人は介在しない。
- `validate-docs.py` の ERROR 0 は**必要条件であって十分条件ではない**。構造が通っても中身は空でありうる。
  人のゲートでは必ず「仮定リスト」と「未決事項」を先に読む。
