# ドメインモデリングフェーズ（新 P05）の設計材料

RDRA の成果物から DDD のドメインモデルへ写す工程を設計するための、実データ調査の記録。
題材は `~/git/private/hands-on/rdra-p05-library-v3`（図書館システム、P05 まで完了した状態）。
実装側の規約の正本は `github.com/creadorz/web-ddd`。このファイルはテンプレ自体の資料なので
`meta/` に置く（展開先へは配布されない）。

## 調査対象の規模

| 項目 | 件数 |
|---|---|
| INFO（情報） | 16（対象内 11 / 対象外 5） |
| ST（状態） | 26 |
| UC | 70 |
| 状態を動かす UC | 16 |
| P05 のロット | 6（L1〜L6） |

## 1. 集約候補の一次案

**判定規則**: ST が付いている INFO を集約ルートの候補とする。ST を持つ＝守るべき不変条件と
ライフサイクルがある、という意味になるため。ST を持たない INFO は、参照のみならマスタ、
他の集約のライフサイクルに従属するなら構成要素、発生の記録ならイベントに振り分ける。

| INFO | 名称 | 状態数 | 一次案 | 根拠 |
|---|---|---|---|---|
| INFO-001 | 会員 | 4 | 集約ルート | 有効/利用停止/失効/退会のライフサイクルを持つ |
| INFO-002 | 会員カード | 0 | 会員集約の構成要素 | 発行(UC-002)・確認(UC-012)のみ。会員のライフサイクルに従属 |
| INFO-003 | 書誌 | 0 | マスタ（参照） | 状態を持たず、蔵書から参照されるだけ |
| INFO-004 | 蔵書 | 6 | 集約ルート | 在架/取置中/貸出中/配送中/紛失/廃棄済 |
| INFO-005 | 図書館 | 0 | マスタ（参照） | 登録・変更はあるが業務上の状態遷移を持たない |
| INFO-006 | 予約 | 6 | 集約ルート | 受付済/配送待ち/取置中/受取済/取消/期限切れ |
| INFO-007 | 貸出 | 3 | 集約ルート | 貸出中/延滞/返却済 |
| INFO-008 | 配送 | 3 | 集約ルート | 未出発/輸送中/到着済 |
| INFO-009 | 棚卸 | 2 | 集約ルート | 実施中/完了 |
| INFO-010 | 蔵書発注 | 2 | 集約ルート | 発注済/入荷済 |
| INFO-011 | 廃棄記録 | 0 | イベント記録 | 蔵書の廃棄(UC-021)に伴って発生する記録 |

対象外（INFO-012〜016）はブリーフ 2 節でスコープ外と決まっているので母集団に入れない。

**この一次案は確定ではない。** 集約ルート候補 7 件のうちいくつを本当に分けるかは、次節の
交差を見て決める判断が要る。

## 2. 集約をまたいで状態が動く UC

状態を動かす UC 16 件のうち、**2 つ以上の INFO の状態を同時に変えるものが 7 件**ある。

| UC | 同時に動く情報 | 内訳 |
|---|---|---|
| UC-010 | 3 | 蔵書:取置中 + 予約:配送待ち/取置中 + 配送:未出発 |
| UC-011 | 2 | 蔵書:在架 + 予約:期限切れ |
| UC-012 | 3 | 蔵書:貸出中 + 予約:受取済 + 貸出:貸出中 |
| UC-013 | 2 | 蔵書:在架 + 貸出:返却済 |
| UC-016 | 3 | 蔵書:在架/配送中 + 予約:取置中 + 配送:輸送中/到着済 |
| UC-017 | 2 | 蔵書:紛失 + 棚卸:実施中/完了 |
| UC-020 | 2 | 蔵書:在架 + 発注:入荷済 |

**7 件すべてに INFO-004 蔵書 が関与している。** 蔵書がこのシステムの交差点であり、
集約境界の判断はここに集中する。

RDRA はこの事実を正しく記録しているが、**1 トランザクションにするのか、集約を分けて
結果整合にするのかは決めていない**。RDRA にその必要がないため当然で、欠陥ではない。
新フェーズが引き受けるのはこの判断と、判断理由の記録（ADR）である。

## 3. 集約はロット境界をまたぐ（フェーズの置き場所の根拠）

P05 のロット割り当てと、状態を変える UC を突き合わせた結果。

| 情報 | 状態を変える UC | またぐロット |
|---|---|---|
| 蔵書 | UC-010, 011, 012, 013, 016, 017, 020 | L4, L5, L6 |
| 予約 | UC-008, 009, 010, 011, 012, 016 | L3, L4, L5 |
| 貸出 | UC-012, 013, 014 | L5 |
| 配送 | UC-010, 015, 016 | L4 |

蔵書と予約が 3 ロットずつにまたがる。**ドメインモデリングをロット単位（ハンドオフの後）で
行うと、蔵書が 3 回別々に設計される。** ドメインモデリングはハンドオフより前に置く必要がある。
これが案1（新 P05 = ドメインモデリング、ハンドオフを P06 へリネーム）を採る実データ上の根拠。

## 4. RDRA 側から写せないもの（新フェーズが埋める穴）

### 4-1. 状態遷移の規則が無い

ST テーブルは**状態の列挙**であって遷移図ではない。「どの状態からどの状態へ、どの UC を契機に、
どんな条件で遷移するか」は書かれていない（説明列に「期限は 7 日」のような断片があるだけ）。
DDD ではこれがエンティティの振る舞いそのものになるため、新フェーズで遷移表を作る必要がある。

置き場所は `docs/domain/` にする。`docs/rdra/04-system/` に足すと RDRA の範囲を超える。

### 4-2. 業務ルールが空のことがある

`docs/rdra/04-system/README.md` の「条件・バリエーション」節は、この題材では
**未記入**（RDRA フェーズ3 を実施するかは G1 で判断する設計のため、実施されていない）。

振る舞いの出どころとして想定していた 2 系統のうち 1 つが欠ける。指示テンプレは
**この節が空の場合の分岐**を持つ必要がある。空なら ST の遷移条件と UC の記述から引き、
引けないものは未決へ上げる。埋められたことにしない。

### 4-3. UC と UseCase の粒度が違う

RDRA の UC は業務の単位、`web-ddd` の usecase は `Employee/add` のような操作単位。
対応表は 1 対多を許す形にする。

### 4-4. 境界づけられたコンテキストが導けない

RDRA はシステム境界（3 層目）を 1 つとして扱うので、システム内部の分割の材料が無い。
この題材の規模（集約候補 7、UC 70）では単一コンテキストで足りるため、当面は扱わない。
扱う必要が出たら、その時点で論点として立てる。

## 5. 指示テンプレに必ず書くこと

- **INFO をそのままエンティティにしない。** 属性は INFO から、振る舞いは ST の遷移条件と
  条件・バリエーションから引く。書かないと、DDD の形をしているが集約が無いコードになる。
- **集約をまたぐ UC は一覧にしてから判断する。** 1 件ずつその場で決めると、同じ情報に対して
  別の判断が混ざる。
- **集約境界の判断理由は ADR に書く。** `docs/domain/README.md` には結果だけを書く。
- **TypeScript のコード断片を書かない。** 実装規約の正本は `web-ddd` 側にある。
  書くのは名前と対応関係だけ。

## 6. 検証で機械判定にできるもの

新しい ID 接頭辞は増やさない（増やすと改修箇所が 9 つに波及する）。エンティティは名前で参照する。

- どのエンティティにも写っていない対象内 `INFO-xxx` が 0 件
- どの状態遷移にも現れない `ST-xxx` が 0 件
- 対応する UseCase が無い `UC-xxx` が 0 件（対象外 UC を除く）
- 集約をまたぐ UC が、整合方式（トランザクション / 結果整合）を決めずに残っていないこと
