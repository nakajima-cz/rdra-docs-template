RDRA 公式サンプルの初期要望（図書館システム）を題材に、`rdra-docs-template` の
P01 指示テンプレ（`docs/prompts/p01-requirements.md` / `p01-steps.md`）を実地で通した結果。

- 実施日: 2026-10-31
- 検証リポジトリ: `~/git/private/hands-on/rdra-p01-library`
- 実行者: 別コンテキストのエージェント2体（RDRAフェーズ1 = Step1〜4、RDRAフェーズ2 = Step5〜6）
  - テンプレを書いた本人の前提が補完されるのを避けるため、指示ファイルのみを読ませる形で実行
- テンプレのバージョン: `v1.11.0` + 未タグのプロンプト追加分

# A. 指示テンプレの欠陥

## A-01 `REQ-xxx` がどのステップの成果物か未定義 【必須】

- **期待**: 採番を許可している ID は、すべてどこかのステップのゴール・判定・出力先に現れる
- **結果**: 共通指示は「採番は REQ- / UC- / INFO- / ST- のみ」と `REQ` を許可しているのに、
  `p01-steps.md` の Step1〜9 に `REQ` の語が一度も出てこない。一方で雛形の
  `01-system-value/README.md` は「要求モデル（機能要求 REQ-xxx / 非機能要求）」を置けと言う
- **影響**: 実行者は Step1 の出力先が `01-system-value` であることから推測して書いたが、
  「指示されたステップの範囲を越えない」に触れないか最後まで判断がつかなかった
- **対応案**: Step1 のゴール・判定・出力先に `REQ-xxx` を明記する

## A-02 画面の扱いが正面衝突する 【必須】

- **期待**: 「画面に関して Step5 で何をどこまでやるか」が一意に読める
- **結果**: 共通指示「SCR-xxx / API-xxx の採番はしない。対応表は空のまま残す。それは P02 の仕事。」に対し、
  Step5 の判定は「画面もイベントも紐づかない UC が 0 件」、出力先は
  「`docs/rdra/03-boundary/README.md`（UC 一覧・**画面一覧**・イベント一覧）」。
  「画面一覧は作れ、ただし採番するな」という指示がどこにも書かれていない
- **影響**: 実行者が `ADR-0004` を自力で起こして「名称のみ・採番なし」と決着させた。
  本来はテンプレ側が決めるべき判断が、案件側の ADR になった
- **対応案**: Step5 に「画面は名称のみ列挙する。SCR 採番は P02 で行う」と明記する

## A-03 例示行の削除ルールと「UC・画面を作らない」が衝突する 【必須】

- **期待**: 雛形の例示行の扱いが、全ステップで矛盾なく決まる
- **結果**: 共通指示「雛形の例示行は実内容に置き換えるか削除する。**残したまま完了にしない**」に対し、
  Step1〜4 の「やらない: UC を作らない。画面を作らない」。`03-boundary/README.md` の例示
  `UC-001 認証する` / `SCR-001 ログイン` は、Step1〜4 では置換も削除もできない
- **影響**: 実行者は「出力先ではないので放置」と判断したが、共通指示には反している状態で
  Step4 を完了した。優先順位がテンプレから読めない
- **対応案**: 「自分の出力先ではないファイルの例示行には触らない」を共通指示へ追加する

## A-04 UC の粒度の基準が無い 【重要】

- **期待**: UC の切り方に一定の基準があり、実行者が変わっても件数が大きくぶれない
- **結果**: アクティビティ1件＝UC1件なのか、画面単位なのか、入出力の変わり目なのかが未定義
- **影響**: 実行者の自己申告で **UC 件数は解釈次第で 14〜25件に揺れる**。
  UC 件数は見積りの基礎なので、G1 ゲートの「見積り可能か」の判断根拠が不安定になる
- **対応案**: Step5 に粒度の基準（例: アクターの操作目的が変わるところで切る）を1行入れる

## A-05 「イベント」の定義が無い 【重要】

- **期待**: Step5 の判定に出てくる「イベント」が何を指すか一意に読める
- **結果**: 時間イベント（半年に1回の棚卸）・外部システム連携・帳票のどれを含むのか不明。
  採番規約（`REQ-/UC-/INFO-/ST-` のみ）にイベントの ID が無い
- **影響**: 実行者はイベントを名称のみで扱った（3件）。ID が無いため後工程から参照できない
- **対応案**: イベントの定義を Step5 に書き、ID 体系に含めるか「名称のみ」と明記する

## A-06 「各 UC に入出力が付いている」の入出力が曖昧 【重要】

- **期待**: Step5 で書くべき「入出力」の範囲が、Step6 の担当範囲と重ならない形で定義されている
- **結果**: 画面・イベントのことか、UC が扱う情報まで含むのかが読めない
- **影響**: 実行者は両方書いたが、情報まで書くと Step6（UC×情報の突合）を先取りすることになる
- **対応案**: 「Step5 の入出力は画面とイベントのみ。情報との接続は Step6」と明記する

## A-07 「システム化対象外」の記載先が未指定 【重要】

- **期待**: 対象外の判断が1箇所に集約され、正本が決まっている
- **結果**: `02-external`（アクティビティ表）と `03-boundary`（UC 表）のどちらが正本か書いていない
- **影響**: 実行者が `03-boundary` を正本と決め、`02-external` から参照させた（独自判断）
- **対応案**: 正本を指定する

## A-08 外部システムを UC のアクターにしてよいかが未定義 【検討】

- **期待**: 外部システム起点の UC を作ってよいかが決まっている
- **結果**: Step5 の判定「アクターの紐づかない UC が 0 件」があるため、
  外部システム起点の UC を置くと判定に引っかかる
- **影響**: 書籍販売システムからの入荷通知 UC を作らず、司書の受入 UC に寄せた
  （＝創作しない側を選んだのは正しいが、業務実態と合うかは別問題）
- **対応案**: 外部システムをアクターとして許可するかを明記する

## A-09 `p00-brief.md` の仮定・未決への追記書式が未定義 【重要】

- **期待**: 複数ステップ・複数実行者が追記しても、書式が一定に保たれる
- **結果**: 「1行1件」としか書かれておらず、ステップを跨いだとき追記か書き換えかが不明。
  節の境界が HTML コメントだけで、追記時に見出しを壊しやすい
- **影響**: 1人目の実行者が `### Step N で置いた仮定` という見出し構造を**独自に発明**し、
  2人目がそれに追従した。テンプレに無い規約が現場で自然発生している
- **対応案**: ステップ別の見出し構造をブリーフ雛形に最初から入れる

## A-10 Step1 のゴールに対応する判定項目が無い 【必須】

- **期待**: `p01-steps.md` 冒頭の宣言「ゴールは『状態』で書いてある。判定できる」が全ステップで守られる
- **結果**: Step1 のゴール「システム化対象の『あたり』が付いている」に対応する判定項目が無い
- **影響**: 実行者が自己採点不能と報告。**自分で掲げた原則に自分で違反している**
- **対応案**: 判定項目を足すか、「ここは人が判断する」と明記する

## A-11 Step3「システムで扱うものが区別されている」の表現方法が無い 【重要】

- **期待**: 「扱う／扱わない」の区別をどう記録するかが決まっている
- **結果**: 扱わない情報も `INFO` 採番するのか、別枠に書くのかが書かれていない
- **影響**: 実行者が全件採番し、`本システムで扱う: ○/要確認` という列を独自に追加した
- **対応案**: 表の列構成を雛形で示す

## A-12 図・Mermaid の扱いが無い 【重要】

- **期待**: 図を作るのか作らないのか、作るならどの形式かが決まっている
- **結果**: 雛形は「図は `../../assets/` に実体を置き参照する」と言うが、
  AI が画像をどう作るか（作らなくてよいのか）、Mermaid を本文に埋めてよいかが無い
- **影響**: B-02 の落とし穴と連動して静かな破壊を招く（後述）
- **対応案**: 「図は Mermaid で本文に埋めてよい。ただし ID の定義は必ず表に書く」と明記

## A-13 新規 ADR の日付の扱いが無い 【軽微】

- **期待**: ADR の `updated` 等の扱いが決まっている
- **結果**: 既存 ADR-0001/0002 は `YYYY-MM-DD` のままで、validator も ADR のプレースホルダを警告しない
- **影響**: 実行者が実日付を入れたが、判断は任意だった
- **対応案**: ADR 雛形に記入ルールを1行入れる

## A-14 連続実行時の歯止めが無い 【必須】

- **期待**: 1ステップ1セッションが前提だが、実運用の連続実行でも越境が防がれる
- **結果**: 「次のステップの内容を先取りしない」はあるが、
  1セッションで複数ステップを回すときの対策が無い
- **影響**: **実際に2件の越境が発生**（D-01, D-02）。いずれも実行者が自力で巻き戻したが、
  気づかなければそのまま commit されていた
- **対応案**: 「各ステップの開始時に前ステップの成果物ファイルを読み直し、記憶で進めない」を追加

## A-15 入力の優先順位が書かれていない 【重要】

- **期待**: テンプレの規約と、実際の依頼文が食い違ったときの優先順位が決まっている
- **結果**: 共通指示「会話で補足された内容は入力に含めない」に対し、
  今回の依頼文には「原本を参考に見てよい」とあった
- **影響**: 実行者はテンプレを優先したが、優先順位はテンプレ側に書かれていないため偶然そうなった
- **対応案**: 「この指示文が依頼文より優先される」を明記する

## A-16 「質問してよい5つ」の範囲が広すぎる 【重要】

- **期待**: 本当に人に聞くべきことだけが質問として上がる
- **結果**: 5条件の1つ「コードにも文書にも無い業務事情」が広すぎ、
  **未決25件すべてがこれに該当しうる**
- **影響**: 結果として**一度も質問が発生せず**、全部を仮定・未決へ倒した。
  それが正しい運用なのかテンプレからは読めない
- **対応案**: 「未決のうち、これが決まらないと UC 件数が動くものは人へ上げる」等の基準を足す

## A-17 「決めるのは人」だが実行者が AI 単独のときの扱いが無い 【重要】

- **期待**: 主担当が「人」のステップで、AI 単独実行なら止まるか、明示的に仮定として扱われる
- **結果**: `p01-steps.md` は Step5・Step6 の主担当を「人（AI は整合チェック）」としているが、
  AI 単独で実行された場合の指示が無い
- **影響**: 本来人が決めるべき判断（UC 粒度など）を仮定で埋めた。
  **フェーズ2 の仮定8件中4件がこの性質**
- **対応案**: 主担当が人のステップでは、該当判断を仮定ではなく「要人判断」として別枠に出させる

## A-18 システム化対象の確定結果の置き場が分散した 【軽微】

- **期待**: 1つの判断結果は1箇所に置かれる
- **結果**: `01-system-value/README.md` に「システム化対象の確定は Step5 で行う」と書いたが、
  確定結果は `03-boundary` 側に置かれた
- **影響**: 読み手がどちらを見ればよいか分からない
- **対応案**: 片方から他方へのポインタを雛形に入れる

# B. validator の欠陥

## B-01 ID と名称の対応を検証していない 【最重要】

- **期待**: ID の指す対象が全ファイルで一致していることを検査する
- **結果**: `docs/traceability/screen-uc-api.md` の `UC-001 認証する` と、
  `docs/rdra/03-boundary/README.md` の `UC-001 会員を登録する` が
  **正面から矛盾しているのに `ERROR 0`**。ID の存在しか見ていない
- **影響**: **採番し直した瞬間に、嘘の対応表が静かに成立する。** 実案件で確実に踏む。
  しかも UC-001 が「定義済み」になったため WARN すら消え、痕跡が残らない
- **検証**: 実リポジトリで再現確認済み
- **対応案**: ID 初出時の名称を正本とし、他ファイルでの名称不一致を ERROR にする

## B-02 コードフェンス内の ID を拾わない 【重要】

- **期待**: 図の中に書いた ID も定義として認識される、または警告が出る
- **結果**: validator は誤検出を避けるためコードフェンスを除去してから ID を拾う。
  そのため **Mermaid 図の中だけに書いた ID は「未定義」扱い**になる
- **影響**: 今回はたまたま実行者がこの仕様を知っていて表側にも書いたため無事だった。
  知らない実行者は静かに壊す。A-12（図の指示が無い）と連動する
- **対応案**: 仕様としては正しいので、テンプレ側に「ID 定義は必ず表に書く」と明記する

## B-03 雛形サンプルが残り続けることが構造的に危険 【重要】

- **期待**: 雛形のサンプルが残っていても害が無い、または検出される
- **結果**: `SCR-001` / `API-001` / 対応表の行は**実体があるため validator は正常と判定し続ける**
- **影響**: B-01 と組み合わさると、案件の実 ID と雛形サンプルが衝突しても気づけない
- **対応案**: 雛形サンプルに「サンプル」マーカーを入れ、実採番と衝突したら警告する

# C. プロセス・運用上の問題

## C-01 ブリーフの転記漏れが UC を丸ごと消す 【最重要】

- **期待**: 原典の要望がブリーフに漏れなく転記され、欠落があれば検出される
- **結果**: 原典にある「利用者はWebで各図書館の蔵書を確認できる」をブリーフへ転記し損ね、
  **蔵書検索という UC が丸ごと落ちた**。他に「仮置き棚」「窓口受付」も欠落
- **影響**: **validator では原理的に検出不能**（構造は完全に整合しているため）。
  今回発見できたのは、依頼文で例外的に原典を参照させたからで、テンプレの力ではない
- **対応案**: 「原典 → ブリーフの転記差分を AI に指摘させる」工程を P00 に足す

## C-02 ブリーフ作成が検証対象外になっている 【最重要】

- **期待**: 唯一の入力であるブリーフの品質が担保されている
- **結果**: 「1〜5節は人が記入する」とだけ書かれ、人の作業なので検証不要という前提になっている
- **影響**: C-01 の直接の原因。入力が壊れていれば後工程はすべて壊れる
- **対応案**: ブリーフにも完了条件（原典との差分確認）を設ける

## C-03 未決事項を人へ上げる導線が無い 【重要】

- **期待**: たまった未決が、しかるべきタイミングで人に確認される
- **結果**: 未決25件がブリーフに蓄積したが、**誰にいつ確認するかのトリガーがテンプレに無い**
- **影響**: G1 ゲートで人が全部読む前提になっているが、25件を読み切る保証が無い
- **対応案**: 「UC 件数が動く未決」を優先度付きで先頭に出させる

## C-04 Step5 ↔ Step6 の往復の記録方法が未指定 【軽微】

- **期待**: 往復したことが記録に残る
- **結果**: git は線形なので表現方法が決まっていない
- **影響**: 実行者が `step5-2:` という連番を独自に発明した（結果的に妥当）
- **対応案**: コミットメッセージ規約として明記する

# D. 実行中に実際に起きた越境事故

いずれも実行者が自力で気づき修正したが、気づかなければ commit されていた。

## D-01 Step1 で Step3 の ID を先取りした 【実際に発生・修正済み】

- **期待**: Step1 では Step2〜4 の内容を書かない
- **結果**: Step1 の時点でブリーフ6・7節に Step2〜4 の仮定をまとめて書き込み、
  `INFO-008` `ST-004` という**未採番の ID まで先に書いた**
- **影響**: 気づいて「（Step N 実行時に追記する）」へ巻き戻してから commit した

## D-02 ADR に未採番の ID を書いた 【実際に発生・修正済み】

- **期待**: 存在しない ID を参照しない
- **結果**: `ADR-0003` の「影響」に「情報モデルの `INFO-010` 図書館」と書き、Step3 の採番を Step1 で先取りした
- **影響**: dangling 参照で ERROR になるおそれがあった。「情報の採番は Step3 で行う」へ書き換えて回避

## D-03〜D-07 書きかけて止めたもの 【越境せず】

- Step2: BUC に UC 名・`UC-xxx` を振りかけた → Step5 の領分なので中止
- Step2: 「蔵書を検索する」アクティビティを入れかけた → ブリーフに無い（原典のみ）ため不採用
- Step4: `stateDiagram` を書きかけた → **「遷移は書かない」の一文で停止**
- Step5: 貸出条件の中身（冊数上限・延滞）を書きかけた → Step7 の範囲なので UC 名と未決のみに
- Step5: `ST-010`「取置中」の追加、`INFO-012` の採番、「システム管理者」アクターの創作を、
  それぞれ書きかけて中止（根拠がブリーフに無いため）

# E. 意図どおり機能した制約（残すべきもの）

## E-01 「ブリーフに無いことは未確定として扱う」

- **期待**: 一般知識による創作を止める
- **結果**: 貸出期間14日、延滞料金、予約取置7日、ISBN、書誌/所蔵の分離などを書きたくなる場面が
  常にあったが、全部を仮定・未決へ逃がせた。**仮定27件・未決25件はほぼこの制約の産物**
- **評価**: 最も効いた制約

## E-02 「思いつかない状態を無理に捻り出さない」（Step4）

- **期待**: 状態の創作を止める
- **結果**: 実行者の自己申告で「これが無ければ会員に『有効/退会/停止』、購入に『発注/入荷』を
