なぜ API の後か

web-ddd のフローが openapi → domain → interface → test → impl。 API 契約が先、ドメインが後。RDRA 側も P04 で API を採番するので順序が合う。

なぜハンドオフの前か

集約がロット境界をまたぐため。後ろに置くと同じ集約が複数回、別々に設計される。 実データで確認した（9枚目）。

RDRA 側から写せなかった 3 つ

状態遷移の規則が無い

ST は状態の列挙で遷移図ではない。どの状態からどこへ、どの UC を契機に、 どんな条件で、が無い。docs/domain/ に遷移表を新設する。

業務ルールが空だった

「条件・バリエーション」節は未記入（RDRA フェーズ3 の実施は G1 判断のため）。 空のときの分岐が要る — 引けないものは未決へ上げ、埋めたことにしない。

コンテキスト境界は導けない

RDRA はシステム境界を 1 つとして扱う。この規模（集約 7・UC 70）では 単一コンテキストで足りるので、当面は論点に立てない。
