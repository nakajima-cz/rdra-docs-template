（「遷移できない組み合わせ…」など）

例示を書く前の3つの確認

閾値つき規則に文面の例を添えない 引き元を「欄の名前」で指定しない 実在IDを使うなら題材を開いて確かめる

0件への最後の一手

13周目 — 穴が隣へ移った

足した規定: 結果整合とした UC は、待ちに入る操作と抜ける操作で必ず割る

浮いたケース: 仮置き棚配置は待ちに入るだけで、抜けるのは別の UC。 指定された割り方が適用できない

14周目 — 除外条項を添えた

足した一文: 抜ける操作がその UC の中に無いなら割らない

結果: 仮置き棚配置は1行、配送と棚卸は2行。 「抜ける操作がこの UC の中にあるか」の1問で機械的に決まった

検査として残した手順

「必ず〜する」と書いたときは、〜できない入力が母集団にあるかを確かめる。 検証の依頼文にも「今回足した除外条項が、別のケースを新たに壊していないか」を入れる。

14周目は実行者が全ケースに当てて「新条項は既存の経路で決まる行を一つも奪っていない」と確認した。

除外条項を同時に書く9 / 11
記録しておくもの

消すと結果が変わる一文

判定は生成側だけで行う。「集約が消えれば一緒に消えるか」で判定しない
退会・廃棄済・返却済という終端状態で情報を消さない設計では常に偽になり、「含む情報」が全行空になる
集約ルートを生成する UC は、状態モデルで遷移元を持たない状態の遷移 UC とする
情報モデルに生成 UC の欄が無いため、この一文が無いと判定を始める起点が無く作業が止まる
状態を1つも変えない下位操作には行を作らない（照合の登録など）
これが無いと5節が API 個票38件に引きずられ、UC 単位の対応表ではなく API 単位の表になる
実装規約が読めない場合は命名を自分で確定しない。暫定名＋未決へ。読めないことを理由に作業を止めない
参照先 URL は private リポジトリで実際に 404 だった。この一文が無ければ Step4 で止まっていた
