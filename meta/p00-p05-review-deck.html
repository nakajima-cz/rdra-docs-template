(a) 指示が無くて止まった (b) 指示同士が矛盾した (c) 指示に従ったら別の判定が×になった (d) 重要な判断を実行者が自分で決めた。 表の列構成や語彙選択は数えない。

正本を二重にしない

後工程の文書に前工程の中身を書き写させない。参照だけにする。 写した時点で、どちらが正しいか分からなくなる。 例外は数値の達成基準だけ（実装側がそのファイルだけ見て判定するため）で、転記したら出典を併記する。

判定の母集団を先に決める

雛形のサンプル ID は900番台に固定し、 「全判定の母集団から除外する」と各フェーズの指示文に書く。 説明文にリテラル ID を書かない（SCR-xxx の形で書く）。

完了条件は判定できる形にする

「正しく動くこと」は完了条件にしない。 実行できるコマンドか人が○×を付けられる文のどちらかにする。 実装CLIはこれが無いと止まれない。

数え方を1行で定義させる

「3ステップ以内」は、画面表示を数えるかで 3 にも 4 にもなる。 数えられる基準を持つ画面は数え方の定義を文書化させ、決まらなければ未決へ倒す。

やらないことの線引きは「操作できるか」

対象外の業務をボタン・列・入力欄にするのは禁止。 人の作業の案内文として書くのは可。この1行で、モックへの機能の混入が3件止まった。

止めるか続けるかを分ける

書けないなら止める。書けるが欠けがあるだけなら未決へ上げて続ける。 線引きが無いと、軽い欠けでフェーズ全体が止まる。

1タグを push するか

ローカルに v1.12.0 〜 v1.16.0 の 5本が溜まっている。push すると copier update で既存リポジトリへ配布され、取り消しにくい。

2実案件を1本通すか

テンプレは図書館システムで固まった。 次は実案件で1本通し、そこで出た欠陥だけを昇格させる段階。 検証用リポジトリでの周回は、同じ題材ではこれ以上の収穫が見込めない。

3図書館システムの未決3件に答えるか

答えれば実装ハンドオフまで完全に通った状態になる。 検証用なので答えずに止めてもよい。
